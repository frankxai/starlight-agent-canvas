# Website directions

The canvas now holds an editable source-backed website plan. Open **Shape website directions** from the workspace. Its focused workbench connects source observations, up to three copy/concept directions, real routes, proposed repository files, acceptance criteria and asset placements. All editing and saving remains keyless and local under `AGENT_CANVAS_HOME`.

An authored example explores a proposed `/about` page for the accepted Canvas product. It uses the repository contract at main77df15d and contains real copy, three considered alternatives and a section-level implementation brief. It is authored arrangement, not model generation. It does not replace the canvas first screen. Its desktop/mobile captures are explicitly reference-only; no site screenshot or customer approval is invented. Import a strictly validated `starlight.websitePlan.v1` JSON plan to bring your own observations, captures and approved media references.

The canonical plan is metadata on one `design_brief` output node using existing v0.1 node kinds. Typed `site_snapshot`, `design_option`, section/CTA/funnel and asset-placement nodes are materialized read-only graph views, with stable IDs, source timestamps and references to that plan. A snapshot artifact preserves its source notes and chunks. Positions remain editable. Content belongs in the workbench; current projections regenerate together on save. Retired projections and unrelated nodes/links remain intact. There is no second store or scheduler.

Save uses the existing per-canvas lock and atomic write. An expected plan hash prevents another browser or agent from silently replacing a newer plan. The workbench preserves unsaved text in this tab's session storage and offers draft download; session recovery is convenience, not a substitute for saving. On conflict, inspect the saved version, keep/download your draft and reconcile the edits. Opening the saved version keeps the previous draft available for download. A timeout can follow a completed save, so inspect before retrying.

Choosing a saved direction writes a checkpoint of its source state and records a `user_assertion` containing the option ID, checkpoint ID, SHA256 plan hash and time. This is a local choice, not authenticated identity or release authorization. The operation is serialized with mutations; identical retries reuse a verified selection. Editing the plan clears the earlier selection. Export verifies both current plan and original checkpoint before creating a portable `starlight.websiteImplementation.v1` JSON or Markdown brief. It includes the chosen copy, target repository/issue, route/file/asset references, responsive/accessibility/acceptance constraints and unresolved evidence. It never writes another repo, runs an agent, deploys, publishes or sends messages.

Choices with missing or corrupt checkpoint evidence are shown as unverified. Explicitly choosing that saved direction again captures a new current source state without deleting damaged evidence. A malformed or duplicate plan authority has a hash-guarded replacement path: download the original canvas, load/import a valid draft and choose **Replace invalid plan with draft**. Original nodes and metadata remain as unverified evidence; the replacement establishes one current plan. Identical save retries are safe after a lost response. New edits made while a request is pending remain unsaved rather than being overwritten by its response. Previous drafts opened against a saved version persist in this tab's session storage and remain downloadable after reload; storage exhaustion blocks replacement until the draft can be preserved. Incomplete text fields also recover, then receive actionable validation before save. Browser-tab storage is not cross-device backup.

The authored example carries a machine-readable content-origin declaration into the exported packet. Source/proposal text is fenced as untrusted evidence in Markdown; embedded instructions do not grant authority to a builder. The browser fetches export files with inline failure messages and preserves focus during saves/choices. API errors do not expose machine paths. As with existing trusted local Canvas import, any local client can assert a selection; the absence of an MCP selection tool is a workflow convention, not authentication. Remote mode remains outside this localhost-only release boundary.

Loading an example or importing another plan preserves an existing dirty draft in the same tab's backup list first. Editing the example marks its declared content origin as `edited_authored_example`. Invalid browser recovery evidence is retained under a content-hash key, so repeated reloads do not multiply it. Relative asset references reject encoded traversal, schemes, control characters and machine paths. Public HTTPS references remain syntax-checked declarations; target ownership, live accessibility and actual media/provenance bytes still need independent verification.

Agent tools: `get_website_plan`, `save_website_plan` and `export_website_implementation`. Updates require the previous plan hash; there is no direction-selection MCP tool. Local browser clients share the same store and privacy boundary. Canvas import is a trusted local operation; it does not authenticate a person's identity or make imported choices approvals. Checkpoint files must exist and validate in this home before exports work.

Media readiness requires sidecar, generation-ledger and taste-ledger references plus alt text or transcript in the schema. Readiness remains a declaration. Each placement now supports editing its text and references, plus **Check local media evidence**. Select the existing image/video, its sidecar and one JSON object or JSONL line from each ledger. Each selected record is limited to 128 KiB; media is limited to 25 MiB. Reads are serialized across placements, cancellable and bounded by a 15-second deadline. File bytes remain in browser memory and are cleared on navigation; only the bounded hash report is added to the existing draft, save, checkpoint and export path.

The comparison checks an image/video signature, SHA256 media hash, file basename, media type, generation details and agent session against the supplied sidecar and generation record. The taste record must carry the same record ID and hash. Raw sidecar and selected-record hashes preserve exact input bytes, including a UTF-8 BOM; raw prompts, models, sessions and preference text are not copied into the report. These are bounded positive-field comparisons, not validation against the external VIS schema or an authenticated ledger lookup. A supplied matching record does not establish its presence in the canonical ledger. A signature does not establish valid decoding, playback or safe content. The file basename does not establish source location, and the browser clock is a reported comparison time. Imported reports remain local assertions.

A successful comparison creates a `starlight.websiteMediaCheck.v1` report without promoting readiness or granting publication. Licensing, source location, generator authenticity, playback and release evidence remain explicit gaps. Changing a media or provenance reference removes the earlier report and cancels its pending comparison. Copy edits made while hashing are preserved; late results cannot overwrite a changed placement. Failure or cancellation retains the current draft and previous report. Save and choose the updated plan before exporting it. Incomplete placement text recovers in the tab and requires reconciliation before save; file input selections are deliberately not persisted.

References never trigger file reads or remote fetches. Absolute machine paths, out-of-repository proposed files, unknown fields, duplicate entity IDs, unresolved placement IDs, oversized plans, credentialed URLs and obvious private/local URLs are rejected. Public URL references use HTTPS without query strings/fragments; DNS is not resolved because no URL is fetched. A syntactically public hostname is not proof of public accessibility.

Implemented verification covers save/reload, source-scoped export, checkpoint corruption, simultaneous writers, stale selection, media provenance declarations, invalid/private URLs, bounded imports, keyboard choice, mobile/reduced-motion rendering, draft recovery and visible conflict/import failure. Actual screenshot inspection and independent exact-revision review are release evidence, recorded in the PR. A real design-partner walkthrough and matched native-app/Markdown outcome benchmark remain open in issue27. Screenshot capture/import automation, live provider acceptance, scoped PR application and release evidence remain integration work. This planning artifact does not establish paid-product success or the completed Starlight interface program.

The serious comparison for this slice is a manual SHA256 check followed by reading the sidecar and two ledger records and carrying the findings into Markdown. The workbench joins that comparison to editable placements, recoverable drafts and checkpoint-linked export. ## Optional website generation

The focused workbench can request three complete page directions from OpenAI or Anthropic. Editing, examples, imports, saving, local media checks, choices and export continue to work without keys. Generation stays disabled until the local operator sets `AGENT_CANVAS_WEBSITE_GENERATION=1`, an explicit `AGENT_CANVAS_WEBSITE_PROVIDER` (`openai` or `anthropic`), `AGENT_CANVAS_WEBSITE_MODEL` supporting native structured output, and that provider's server-only API key. This uses API billing, not a Codex or Claude CLI subscription. No default model, automatic retry, provider fallback, tools or autonomous execution is configured. `AGENT_CANVAS_ALLOW_REMOTE=1` disables generation; the single-user local app has no authenticated hosted spending boundary.

Before sending, **Review the text that will be sent** shows the source identity, observation date and notes, brief, and section text/acceptance/accessibility constraints. These are the only fields forwarded. Media bytes, provenance records, target paths, other canvas nodes and native chat history are excluded. Text the operator includes in those selected fields is disclosed to the configured provider. Provider retention policies still apply; OpenAI requests set `store:false`, which is not a promise of zero retention.

The existing AI SDK is not a wired provider integration. This slice uses a narrow server-only first-party REST adapter with no dependency addition: [OpenAI Responses structured output](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses) and [Anthropic Messages structured output](https://platform.claude.com/docs/en/build-with-claude/structured-outputs). A shared minimal JSON schema constrains the response; local validation additionally checks three distinct IDs/titles/headlines, exact section coverage, prose bounds and literal source quotes. Quote presence establishes only a match in the observations. It does not establish the truth of the proposal, current product readiness or release authorization. Review claims yourself.

Generation accepts up to six sections and 32 KB of selected source text, allows one provider call at a time per local server process, caps output at 6000 tokens and response bytes at 180 KB, and has a 60-second server deadline. The browser waits at most 65 seconds and can stop its request. Abort, refusal, truncated output, invalid copy, provider rejection and a second active request preserve the draft. A stop or lost response can follow provider processing and billing; inspect before a deliberate retry. Restarting the server does not retract a remote request already processed.

Each direction has its own `sectionCopy` and supporting `sourceQuotes`. Routes, repository files, acceptance/accessibility constraints, source identity and media provenance retain their original plan values. Review the generated proposal before using it as a draft. If the draft changes during generation, replacement is blocked and the proposal remains downloadable for reconciliation. The current dirty draft must be backed up before replacement; exhausted or unreadable browser backup storage blocks replacement. The proposal itself recovers from this tab's session storage. Unverified proposal storage is retained for inspection instead of overwritten. Tab storage is convenience, not cross-device backup.

After applying, edit the complete page within each direction's editor. Shared section editors retain the base page and implementation details; directions with section-specific copy export their own words and actions. Saving still uses one canonical plan and the existing lock/hash guard. Choosing still checkpoints the exact reviewed plan. Export merges only the selected direction's prose/actions onto the preserved implementation constraints. Later edits clear the selection. Legacy plans without direction-specific sections continue exporting their shared page copy.

The plan and packet carry declared `model_generated` or `edited_model_generated` origin and `starlight.websiteGeneration.v1` metadata: provider, requested/returned model, time, exact selected-input/output/prompt SHA256 values and `local_assertion` authority. These hashes describe the original request/output; subsequent human edits are covered by the current plan and selection checkpoint hashes. Imported metadata is forgeable and does not authenticate the provider or prove a bill, ownership or customer approval. CI uses explicitly synthetic outputs and intercepted provider responses; live generation, copy-quality acceptance and a matched manual Codex/Claude drafting benchmark remain separate open evidence in issue27.
