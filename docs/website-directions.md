# Website directions

The canvas now holds an editable source-backed website plan. Open **Shape website directions** from the workspace. Its focused workbench connects source observations, up to three copy/concept directions, real routes, proposed repository files, acceptance criteria and asset placements. All editing and saving remains keyless and local under `AGENT_CANVAS_HOME`.

An authored example explores a proposed `/about` page for the accepted Canvas product. It uses the repository contract at main77df15d and contains real copy, three considered alternatives and a section-level implementation brief. It is authored arrangement, not model generation. It does not replace the canvas first screen. Its desktop/mobile captures are explicitly reference-only; no site screenshot or customer approval is invented. Import a strictly validated `starlight.websitePlan.v1` JSON plan to bring your own observations, captures and approved media references.

The canonical plan is metadata on one `design_brief` output node using existing v0.1 node kinds. Typed `site_snapshot`, `design_option`, section/CTA/funnel and asset-placement nodes are materialized read-only graph views, with stable IDs, source timestamps and references to that plan. A snapshot artifact preserves its source notes and chunks. Positions remain editable. Content belongs in the workbench; current projections regenerate together on save. Retired projections and unrelated nodes/links remain intact. There is no second store or scheduler.

Save uses the existing per-canvas lock and atomic write. An expected plan hash prevents another browser or agent from silently replacing a newer plan. The workbench preserves unsaved text in this tab's session storage and offers draft download; session recovery is convenience, not a substitute for saving. On conflict, inspect the saved version, keep/download your draft and reconcile the edits. Opening the saved version keeps the previous draft available for download. A timeout can follow a completed save, so inspect before retrying.

Choosing a saved direction writes a checkpoint of its source state and records a `user_assertion` containing the option ID, checkpoint ID, SHA256 plan hash and time. This is a local choice, not authenticated identity or release authorization. The operation is serialized with mutations; identical retries reuse a verified selection. Editing the plan clears the earlier selection. Export verifies both current plan and original checkpoint before creating a portable `starlight.websiteImplementation.v1` JSON or Markdown brief. It includes the chosen copy, target repository/issue, route/file/asset references, responsive/accessibility/acceptance constraints and unresolved evidence. It never writes another repo, runs an agent, deploys, publishes or sends messages.

Choices with missing or corrupt checkpoint evidence are shown as unverified. Explicitly choosing that saved direction again captures a new current source state without deleting damaged evidence. A malformed or duplicate plan authority has a hash-guarded replacement path: download the original canvas, load/import a valid draft and choose **Replace invalid plan with draft**. Original nodes and metadata remain as unverified evidence; the replacement establishes one current plan. Identical save retries are safe after a lost response. New edits made while a request is pending remain unsaved rather than being overwritten by its response. Previous drafts opened against a saved version persist in this tab's session storage and remain downloadable after reload; storage exhaustion blocks replacement until the draft can be preserved. Incomplete text fields also recover, then receive actionable validation before save. Browser-tab storage is not cross-device backup.

The authored example carries a machine-readable content-origin declaration into the exported packet. Source/proposal text is fenced as untrusted evidence in Markdown; embedded instructions do not grant authority to a builder. The browser fetches export files with inline failure messages and preserves focus during saves/choices. API errors do not expose machine paths. As with existing trusted local Canvas import, any local client can assert a selection; the absence of an MCP selection tool is a workflow convention, not authentication. Remote mode remains outside this localhost-only release boundary.

Agent tools: `get_website_plan`, `save_website_plan` and `export_website_implementation`. Updates require the previous plan hash; there is no direction-selection MCP tool. Local browser clients share the same store and privacy boundary. Canvas import is a trusted local operation; it does not authenticate a person's identity or make imported choices approvals. Checkpoint files must exist and validate in this home before exports work.

Media readiness requires sidecar, generation-ledger and taste-ledger references plus alt text or transcript in the schema. These are declarations; the packet still requires verification of actual asset bytes and provenance. References never trigger file reads or remote fetches. Absolute machine paths, out-of-repository proposed files, unknown fields, duplicate entity IDs, unresolved placement IDs, oversized plans, credentialed URLs and obvious private/local URLs are rejected. Public URL references use HTTPS without query strings/fragments; DNS is not resolved because no URL is fetched. A syntactically public hostname is not proof of public accessibility.

Implemented verification covers save/reload, source-scoped export, checkpoint corruption, simultaneous writers, stale selection, media provenance declarations, invalid/private URLs, bounded imports, keyboard choice, mobile/reduced-motion rendering, draft recovery and visible conflict/import failure. Actual screenshot inspection and independent exact-revision review are release evidence, recorded in the PR. A real design-partner walkthrough and matched native-app/Markdown outcome benchmark remain open in issue27. Screenshot capture/import automation, live model generation, scoped PR application and release evidence are later integration work. This useful planning artifact does not establish paid-product success or the completed Starlight interface program.
